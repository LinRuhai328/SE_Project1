## 2. 已选路线与项目边界

暂定名称：二手商品预约交易系统。

已选路线：预约面交型。主线为审核发布、买家预约、卖家确认、线下交付、确认完成，集中分析权限、状态、并发和操作记录。

建议先以单件实物为场景。校园和普通同城都可以采用预约面交，面向哪些用户仍待选择；校园场景也不自动意味着必须接入校园身份认证。平台帮助用户发布和查找物品、预约交易、确认结果，并帮助管理员审核商品、处理举报和查询操作记录。

第一版讨论范围：

1. 账号注册、登录和角色权限。
2. 商品草稿、提交审核、审核驳回、发布、修改和下架。
3. 按关键词、分类、价格区间和商品状态组合查询。
4. 单件商品预约、取消、卖家确认和买家确认完成。
5. 多人竞争、重复请求、旧页面操作和关键状态变化的处理。
6. 根据交易关系和状态控制联系方式访问。
7. 举报处理、分类及状态统计、关键操作记录。

建议暂不纳入真实支付、物流接入、站内即时聊天、推荐算法、信用评分和自动纠纷仲裁。线下付款及交付由双方自行完成，平台中的“完成”仅表示当事人确认交易完成。这是范围建议，仍需向甲方确认。

## 3. 用户角色与主要目标

买家、卖家是同一普通用户在不同交易中的业务角色，无须先设计成互斥账号。管理员权限单独授予，公开注册接口不能自行创建管理员。

| 角色 | 主要目标与建议权限 |
|---|---|
| 买家 | 查询商品，预约非本人发布的可交易商品，取消自己的预约，查看本人的交易记录，在允许状态下查看对方联系方式，确认交易完成，提交举报 |
| 卖家 | 维护自己的商品，提交审核，查看本人商品的预约，接受或拒绝预约，在允许状态下查看预约者联系方式，查询本人发布与成交统计 |
| 管理员 | 审核商品，说明驳回理由，处理举报和违规商品，查看与管理职责有关的操作记录及汇总数据 |

管理员不能代替买家确认交付，也不能直接改写商品价格、交易对手或历史交易结果。需要怎样处理违规及交易争议，留待访谈确认。

## 4. 用一笔交易串起主要流程

1. 卖家填写标题、描述、分类、价格等商品信息，保存草稿。
2. 卖家提交审核；管理员通过后商品公开发布，驳回时给出原因。
3. 买家按条件查找商品并发起预约。
4. 系统检查当前权限和商品状态，第一个在服务端成功建立有效预约的买家占用商品，商品立即进入“已预约”，其他买家不能再预约；卖家随后只处理这一笔预约。
5. 卖家接受后，交易进入“待交付”；此时双方才获得查看对方联系方式的权限。
6. 双方线下交付；买家在系统中确认完成，商品进入“已售出”，交易进入“已完成”。

建议在访谈中围绕每一步追问“谁能做、什么条件下能做、失败时怎么处理、结果怎样检查”，而不是只问是否需要某个页面。

### 商品与交易分开记录

同一商品可能先后被多人预约，但任一时刻最多存在一笔有效预约。以前取消或被拒绝的记录仍须保留，因此商品和交易不能合并为一条不断覆盖的记录。

建议商品状态：草稿、待审核、审核驳回、已发布、已预约、已下架、已售出。

建议交易状态：待卖家确认、待交付、已取消、已拒绝、已中止、已完成。其中“待卖家确认”和“待交付”属于有效预约；“已中止”用于管理员违规下架等导致的终止，并区别于双方正常取消。第一版暂不默认加入预约超时机制，是否需要自动释放另行确认。

| 操作 | 商品状态变化 | 交易状态变化 | 主要限制 |
|---|---|---|---|
| 提交审核 | 草稿 → 待审核 | 不创建交易 | 仅商品所有者；商品信息合法 |
| 审核通过 | 待审核 → 已发布 | 不创建交易 | 仅管理员；基于当前待审核内容 |
| 审核驳回 | 待审核 → 审核驳回 | 不创建交易 | 记录原因 |
| 修改驳回稿、撤回审核、重新编辑或重新上架 | 审核驳回／待审核／已发布／已下架 → 草稿 | 不创建交易 | 所有者操作；违规限制未解除时禁止重新提交审核 |
| 发起预约 | 已发布 → 已预约 | 创建待卖家确认交易 | 非卖家本人；先成功预约者立即占用，其他买家失败 |
| 卖家接受 | 保持已预约 | 待卖家确认 → 待交付 | 仅该商品卖家 |
| 买家取消或卖家拒绝 | 已预约 → 已发布 | 待卖家确认 → 已取消或已拒绝 | 对应买家或卖家；保留历史记录 |
| 交付前取消 | 已预约 → 已发布 | 待交付 → 已取消 | 暂建议任一交易方可取消并填写原因；须访谈确认 |
| 买家确认完成 | 已预约 → 已售出 | 待交付 → 已完成 | 仅该交易买家；一次生效 |
| 卖家普通下架 | 已发布 → 已下架 | 无有效交易 | 已预约商品暂不允许直接下架，先按约定取消交易 |
| 管理员违规下架 | 已发布或已预约 → 已下架 | 存在有效交易时同时变为已中止 | 记录原因，撤销后续联系方式查询权限 |

“已售出”作为交易终态，不直接返回“已发布”；以后再次出售应创建新的商品。已售商品收到违规举报时，可以屏蔽展示并记录处理结果，但不把历史成交改写为取消。

已预约和已售出的商品暂不允许修改价格、商品描述等交易内容；待审核的商品要先撤回草稿再修改。已发布商品修改后重新审核。管理员审核必须针对当前待审核版本，旧审核页面不能批准已经撤回或变更的内容。

先到先得并立即占用商品的预约规则已由用户确定；上述完整状态划分、卖家接受后的取消权、完成确认人和重新审核范围仍需访谈确认。

## 5. 最值得讨论的冲突和数据规则

### 5.1 多人竞争与重复请求

用户已选择先到先得的预约方式；下面的先后判定是该规则的具体解释，重复请求和冲突返回方式为配套建议。

- 以服务端成功建立有效预约的先后为准，客户端的点击时间或收到响应的时间不作为判定依据。
- 多个买家同时预约同一件商品，只能有一笔有效交易；成功者立即占用商品，其他买家得到“商品已被预约”等明确失败结果。卖家不能在占用期间同时接受其他买家的预约。
- 合法取消或拒绝预约后，保留旧交易记录并释放占用；商品恢复“已发布”时，后续预约重新按先到先得竞争。当前方案不增加候补或自动递补。
- 同一预约请求因双击、网络重试而重复到达时，返回已有结果，不新建第二笔交易。具体技术实现留给后续设计。
- 同一用户换一个请求再次预约已被本人预约的商品，也应提示已有预约，并指向原记录。
- 对已经取消的预约重放旧请求时，不重新抢占商品；确需重新预约时发起新操作并重新检查状态。
- 旧页面上的按钮不能绕过当前状态检查。商品已经被预约、下架或售出时，旧页面提交预约必须失败。
- 接受、取消和确认完成等相互冲突的操作，以实际成功的合法状态变化为依据；后续不满足条件的操作返回冲突，不覆盖前一结果。

### 5.2 联系方式权限

用户已同意卖家接受预约后，交易双方才可通过该交易查看对方联系方式；待卖家确认时尚不开放。

配套建议：在取消、拒绝、中止或完成后停止提供后续联系方式查询。结束后的可见范围仍需讨论确认，不能从用户对开放起点的同意中推定。

公共商品列表、商品详情的公开字段、查询结果、普通统计和操作日志均不返回联系方式。管理员的常规审核和举报查询也不默认展示联系方式。后续查询权限的收回不能撤回对方此前已经看到或自行保存的信息。

权限必须在服务端检查。仅隐藏页面按钮、但直接请求接口仍能取得联系方式，不算满足要求。

### 5.3 数据对象与一致性

| 对象 | 主要信息及关系 |
|---|---|
| 用户 | 唯一账号、登录凭据、管理权限、本人联系方式；一个普通用户可发布多个商品，也可预约他人商品 |
| 商品 | 唯一标识、卖家、分类、标题描述、价格、状态、审核及下架原因；一件商品对应多条历史交易 |
| 交易／预约 | 唯一标识、商品、买家、卖家、状态、预约时商品信息快照、各关键操作时间及原因 |
| 举报 | 举报人、被举报商品、理由、处理状态、处理人和处理说明 |
| 操作记录 | 操作者、时间、动作、对象、处理结果，以及必要的状态变化 |

建议统一规则：

- 价格使用明确的金额单位并限制为合法正数；上限与小数位数待确认。
- 一件商品最多一笔有效预约，买家不得预约自己的商品；一笔交易只能关联一个确定的商品和买家。
- 商品“已预约”必须对应唯一有效交易；“已售出”必须有对应的已完成交易。
- 预约成功、取消、成交和违规中止时，商品、交易及关键操作记录必须一起持久化成功，避免只改其中一部分。
- 交易保留预约时的标题、价格等必要快照；后续改动不能改变历史交易信息。
- 记录取消、驳回、下架和处理结果，保留历史交易，不通过删除旧记录来释放名额或掩盖状态变化。

## 6. 候选需求清单

以下是访谈准备清单，不是正式 REQ 编号，也不计作已确认需求。先通过真实交流决定范围和规则，再生成具有稳定 REQ 编号及十个规定字段的首次完整需求文件。

| 候选项 | 目标 | 重点核对及验收方向 |
|---|---|---|
| F01 | 注册与登录 | 账号唯一；错误凭据不能登录；普通注册不能创建管理员 |
| F02 | 业务角色与对象权限 | 用户可以同时买卖；不能查看或修改他人私有对象 |
| F03 | 商品草稿管理 | 保存和修改本人草稿；非法价格、缺失必填项有明确提示 |
| F04 | 提交与撤回审核 | 合法草稿才能提交；撤回后旧审核操作失败 |
| F05 | 商品审核与发布 | 管理员通过或驳回；仅当前合法版本可发布 |
| F06 | 商品修改与重新审核 | 已发布商品修改后重新审核；交易中不能改动关键内容 |
| F07 | 普通下架与违规下架 | 两类权限、原因和重新提交条件清楚；违规下架中止有效交易 |
| F08 | 多条件商品查询 | 组合筛选关键词、分类、价格、状态；普通用户无权获取审核草稿等私有内容 |
| F09 | 商品预约 | 先到先得，成功后立即占用且只有一笔有效预约；覆盖竞争、重复请求和旧页面 |
| F10 | 取消与拒绝预约 | 按角色、状态处理；恢复可预约状态并保留历史 |
| F11 | 卖家确认交易 | 只能接受自己商品当前有效的预约；重复确认不重复执行 |
| F12 | 买家确认完成 | 仅对应买家可确认；商品及交易同步结束 |
| F13 | 联系方式访问 | 按交易参与人和状态授权；直接接口请求也受限制 |
| F14 | 举报提交与处理 | 举报理由、处理权限和处理结果可查；仅举报不会立即判定违规 |
| F15 | 查询与统计 | 建议卖家看本人商品和成交数量，管理员按分类与状态汇总；口径及可见范围待确认 |
| F16 | 关键操作记录查询 | 普通用户按自身业务关系查询；管理员按职责查询；不得任意修改历史记录 |
| N01 | 查询性能 | 约定测试环境后，以确定的数据量、并发量、响应时间和成功率验收 |
| N02 | 敏感数据保护 | 密码不以明文保存或返回；联系方式不出现在未授权响应及普通日志中 |
| N03 | 已确认结果持久化 | 成功响应后的商品、交易和操作记录，在服务重启后保持一致 |

数量规划为 16 条功能候选、3 条非功能候选。正式划分应按真实目标调整，不为数量拆分同一目标；最终仍须满足至少 15 条已确认需求、至少 10 条功能需求和 3 条非功能需求。

N01 可讨论的起点是：记录测试设备和环境，在一万条商品、二十个并发查询用户条件下，一百次查询至少九十五次在一秒内成功返回，失败或超时计为未达标。此数值借鉴仓库教学模板，只是候选指标，不是甲方已确认的标准。

N02 可以通过检查数据库凭据字段、公开及未授权接口响应和普通日志验证，同时确认正常登录与合法联系方式访问仍然可用。N03 可以通过完成预约、取消和成交后重启服务，再查询商品、交易和操作记录进行验证。具体测试方式在后续实现时落实。

## 7. 两人可以怎样使用这份底稿

用户现已澄清两个项目的归属：二手交易中用户做甲方，多人记账中用户做乙方。二手交易讨论稿用于表达甲方的业务偏好；用户本人的需求分析成果以多人记账的真实访谈为依据。按任务书分别保留角色和过程来源。

建议这样推进：

1. 二手交易轮：你当甲方、雷哥当工程师，参考本稿讨论边界、正常交易、异常、权限和质量要求，由工程师保留实际问答。
2. 多人记账轮：你当工程师，依据已提供的原始转写和[补充提纲](多人记账访谈整理与补充提纲.md)继续澄清，保留实际沟通时间、问题、回答和来源编号。
3. 两人各自将真实访谈和课程约束交给 AI，保存完整输入、首次完整输出及实际工具和模型名称。
4. 各自在自己的仓库保存同一路径的 `requirements.md` 和 `chat.txt`，提交并创建 `lab1-ai-draft`；此时不先覆盖或润色首次输出。
5. 根据自己的初稿核对来源、状态一致性、权限和验收条件，进行补充沟通，记录实际审查结果；正确内容可以保留，不预设必须出现哪些错误。
6. 各自完成最终需求、`lab1-final` 和报告。共用讨论资料不替代个人的访谈、AI 交互、审查和 Git 版本记录。

## 8. 首轮访谈优先弄清的问题

这些问题先问实际需要和理由，再讨论本稿建议，避免把 AI 的建议直接当作甲方的答案。

1. 在已选的预约面交路线下，系统面向哪些人，解决当前交易中的什么问题？是否限定单件物品？
2. 同一个用户能否同时买卖？注册时如何获得普通用户和管理员权限？
3. 商品哪些信息必须填写，价格是否合法怎样判断，审核和驳回由谁负责？
4. 按已选的先到先得规则，一笔预约先占住商品；卖家可以基于哪些理由拒绝，是否需要说明原因？
5. 买家和卖家分别在什么时候可以取消？接受预约以后又不想交易怎么办？
6. 谁确认实际交易完成？对方一直不确认时，第一版系统需要处理到什么程度？
7. 用户已选择卖家接受预约后开放双方联系方式；取消、完成或违规下架后还应不应该能继续查询？
8. 待审核、已发布和已预约的商品分别能否修改？哪些修改要重新审核？
9. 管理员违规下架一个已被预约的商品时，商品、交易和联系方式应怎样同时处理？
10. 需要按什么条件找商品、看哪些统计、查哪些操作记录？对应的访问范围是什么？
11. 能接受怎样的响应速度和数据规模？重启、网络重试等情况下，哪些结果必须保证不丢失或重复？
12. 是否确实需要预约超时或面交纠纷处理？若需要，再明确边界和验收方式。

访谈结束后，优先对照任务书逐项检查有没有漏掉必做范围，再进入首次完整需求生成。
