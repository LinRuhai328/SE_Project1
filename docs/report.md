## 1 项目概况

本项目面向家人、情侣等需要共同记录和核对收支的多人场景，同时支持个人账本。核心目标是让账本、成员、收支记录及其变更可查询、可核对、可追溯，为后续 UML 设计、实现、分析和测试提供明确需求。真实资金托管、支付或转账、自动读取银行或微信／支付宝账单不在第一版范围；AI 分析、AI 模糊查账、储钱罐、代记和多人分摊经甲方确认首版不纳入，保留编号和候选状态。

| 范围 | 本版处理 |
| --- | --- |
| 纳入 | 账号与会话；个人／共享账本；所有者／管理员／普通成员；邀请、退出与交接；记录新增、修改、提交、审核、驳回、撤回、作废、更正；类别字典；多条件查询；分类／成员统计；月度总预算；按自然月结算与重开；截图核对导入；站内通知；操作日志；账本改名与归档。 |
| 不纳入 | 真实资金托管、支付、转账；自动读取银行／微信／支付宝账单；AI 收支分析、AI 模糊查账；储钱罐与省钱目标；代记与多人分摊；多币种。 |
| 明确不做 | 账本、类别、记录和审计的物理删除；只做归档、停用、作废。不承诺断电、机房故障等灾难恢复，只按约定范围验收。 |

### 1.2 关键约束

账本类型创建后不可修改，账本状态为活动或归档；记录状态为草稿、待审核、已审核、已驳回、已撤回、已作废；金额只用人民币、大于零、最多两位小数、单笔上限 999999.99；发生日期不晚于当天；业务日期统一按 Asia/Shanghai（REQ-013、REQ-034）。

## 2 整体业务分析

### 2.1 主要业务流程

| 环节 | 主要行为 | 对应需求 |
| --- | --- | --- |
| 账号与入口 | 注册、登录、会话失效、退出登录。 | REQ-031 |
| 建立账本 | 创建个人或共享账本，邀请指定用户，接受后加入。 | REQ-001—REQ-004 |
| 录入账目 | 手动新增；截图识别后逐条核对、排除或部分提交。 | REQ-005、REQ-011 |
| 提交与审核 | 草稿提交为待审核；审核人通过或驳回（驳回需原因）；本人不能审本人。 | REQ-007、REQ-008 |
| 修改与更正 | 待审核先撤回再改；已审核只能作废或走更正版本，二审后一次替换。 | REQ-006、REQ-009、REQ-010 |
| 查询与统计 | 按类别、成员、日期、金额组合查询；分类和成员分别汇总，收入／支出／净额分列。 | REQ-015—REQ-017、REQ-032、REQ-034 |
| 预算与结算 | 每月一个总支出预算；自然月结算、锁月、版本化快照；只有所有者能重开。 | REQ-018—REQ-020 |
| 通知与审计 | 站内通知规定事件；关键操作留痕，不可改删，保留至复核结束。 | REQ-021、REQ-022 |
| 结束使用 | 账本改名或归档；归档后只读，所有者可恢复。 | REQ-033 |

### 2.2 数据对象与唯一性约束

| 对象 | 关键关系与约束 |
| --- | --- |
| 用户与会话 | 账号唯一；同一账号可有多个会话，会话各自独立失效；退出登录只结束当前会话（REQ-031）。 |
| 账本 | 标识唯一；类型创建后不可改；状态为活动或归档；归档不是删除（REQ-001、REQ-033）。 |
| 成员关系 | 同一用户与同一账本当前最多一条有效成员关系；历史关系保留；退出后可再次被邀请（REQ-002、REQ-003）。 |
| 类别字典 | 每账本一份平铺类别；同一账本内名称不重复；编号稳定，改名不改归属，停用不删除（REQ-032）。 |
| 收支记录与版本 | 从属于单一账本；当前有效版本唯一；旧版本保留，统计只计当前有效版本（REQ-006、REQ-016）。 |
| 凭证／导入批次 | 同一账本内同一平台交易号最多一条有效记录；同图按明细识别，不静默合并同日同额（REQ-012）。 |
| 预算 | 同一账本同一自然月最多一个有效预算值；修改保留审计（REQ-018）。 |
| 结算快照 | 同一账本同一自然月最多一份有效结算；重开后旧快照转为历史（REQ-019、REQ-020）。 |
| 审计记录 | 关键操作记录不可修改、不可删除，保留至复核结束（REQ-021）。 |
| 时间口径 | 发生日期用于归属和统计；创建／提交时间只用于排序、审计和幂等；自然月含起点不含终点（REQ-034）。 |
| 归档 | 只冻结账目业务写；成员退出／交接／管理员任免保留；新邀请不接受（REQ-033）。 |
| 非默认查询 | 默认只查有效；草稿／驳回／撤回／待审核／历史版本按 REQ-035 的权限查看。 |

### 2.3 状态与状态转换

核心对象为收支记录。允许的主线是：草稿→待审核→已审核或已驳回；待审核→已撤回；已驳回／已撤回→修改后重新提交；已审核→已作废；已审核→更正版本（二审后生效）。

| 当前状态 | 操作 | 结果 | 触发者与条件 | 需求 |
| --- | --- | --- | --- | --- |
| 草稿 | 提交 | 待审核 | 录入人，信息合法 | REQ-007 |
| 草稿／已驳回／已撤回 | 修改并重新提交 | 待审核 | 录入人 | REQ-006 |
| 待审核 | 撤回 | 已撤回 | 录入人本人 | REQ-009 |
| 待审核 | 通过 | 已审核 | 所有者／管理员，且非提交人 | REQ-008 |
| 待审核 | 驳回 | 已驳回 | 同上，须填写原因 | REQ-008 |
| 已审核 | 作废 | 已作废 | 所有者／管理员，账期未锁，填原因 | REQ-009 |
| 已审核 | 发起更正并二审 | 新版本生效 | 录入人或管理发起，另一人审核 | REQ-010 |
| 已审核 | 结算锁定 | 账期锁定 | 账期结束、无待审核 | REQ-019 |
| 账期锁定 | 重开 | 未结算 | 所有者填原因 | REQ-020 |

禁止：直接修改待审核、已审核、已作废记录；审核本人记录；普通成员修改他人记录；恢复已作废记录；以旧页面或旧版本覆盖当前结果；在锁定月份内新增、作废、更正或结算。账期状态是独立对象：开放→锁定；锁定→重开→开放；不要与记录状态混用（REQ-019、REQ-020、REQ-029）。

### 2.4 异常、边界与冲突

| 场景 | 明确结果 | 需求 |
| --- | --- | --- |
| 撤回与审核同时发生 | 以服务端先成功者为准；后到操作返回状态冲突并提示刷新。 | REQ-008、REQ-026 |
| 已审核 100 元更正为 120 元 | 审核前统计仍为 100；通过后只按 120 计算；旧版本可查。 | REQ-010 |
| 重复点击、超时重试 | 同一次操作只落一条；重试返回原结果；独立新消费正常新增。 | REQ-014 |
| 重复凭证与同日同额 | 同账本同交易号判重；同图按明细；同日同额只标疑似，由用户确认。 | REQ-012 |
| 结算与补记并发 | 补记先提交则结算因待审失败；结算先锁则补记失败，不自动挪月。 | REQ-019、REQ-026 |
| 单人共享账本 | 禁止自审；所有者可指定第二管理员，或改用个人账本。 | REQ-007 |

| 识别失败或部分行错误 | 不生成零元或空白记录；可跳过错误行，其余候选正常提交。 | REQ-011 |

### 3.3 代表性案例

3.3.1 个人账本、禁止自审与三类角色（REV-011；INT-02-L024—L029、INT-03-L019—L022）

初稿只写“共享账本记录需要审核”，没有定义个人账本是否走同一流程。反例是：单人共享账本没有第二个审核人；个人账本也只有本人，如果同时要求“必须审核”和“禁止自审”，两类账本都无法记账。核对后确定：共享账本必须由他人审核，单人共享账本可指定第二管理员或改用个人账本；个人账本由本人保存或确认即生效，但仍保留版本和审计。验收覆盖“单人共享自审被拒绝”和“个人账本保存即生效”两个方向。

3.3.2 结算后更正与版本（REV-012；INT-02-L045—L048、INT-04-L003—L008）

初稿把结算写成“必须支持”，候选包含账期锁定、新版本和重开，未定结果。反例是：100 元结算后更正为 120 元；如果有待审核记录时结算；结算与补记同时发生；连续点击结算。确定的口径是：按自然月汇总、不计算成员转账；有待审核不能结算；成功后锁月并生成快照；只有所有者能写原因重开，旧快照保留为历史；并发以服务端先成功者为准，重复结算返回原结果。验收要求同时检查结算页快照和明细页当前版本，不能混算。

3.3.3 重复请求、重复凭证与同日同额（REV-013；INT-02-L035—L036、L051—L053、INT-04-L021—L026）

初稿已经写明“不能仅因同日同额静默合并两笔独立真实消费”，也要求“新的独立消费仍可正常新增”；真正没定的是判重键、同图部分导入、待审核是否占用交易号、重试返回结果。最终规则：同一次提交返回原结果；同账本同交易号在待审核或已审核未作废中最多一条；同图按明细识别；同日同额只提示疑似；一组选中记录全成功或全不提交。

3.3.4 范围取舍：真实资金、AI、储钱罐与分摊（REV-014、REV-016；INT-02-L005—L010、INT-05-L003—L016、INT-06-L003—L010、L019—L026）

初稿把真实资金、截图、AI、储钱罐和通知都列为候选。核对后确定：首版只做记账闭环和截图核对、站内通知；真实资金、支付、自动账单同步、AI 分析、AI 模糊查账、储钱罐、代记和分摊都不纳入。AI-08 的补充建议还提出邮箱验证、类别层级、物理删除、分类预算和成员分摊，核对后同样不采纳，保留为后续候选。这样避免为了“看起来完整”扩大范围，也保留了真实依据。

3.3.5 补漏：账号、类别、时间与账本生命周期（REV-015；INT-06-L001—L032）

本人逐条复核时先列出四项可能的缺口，AI-08 只核对判断：全部需求只把“用户已登录”当隐含前提；类别只是字段和查询维度；时间只写“当天／自然月”没有时区；账本只有创建、邀请、退出。这四处不是锦上添花，而是权限验收、分类统计、账期归属和“结束使用”场景的必需规则。INT-06 确认后新增 REQ-031（账号与会话）、REQ-032（类别字典）、REQ-033（改名／归档／不物理删除）、REQ-034（Asia/Shanghai 与自然月／日界）。新增后共 34 条（第六轮后为 35 条），编号从 REQ-031 起，不改原有编号。

3.3.6 个人账本更正与强／疑似重复（REV-017；INT-07-L003—L009）

REQ-007 说个人账本本人确认即生效，REQ-010 又要求另一名审核人；个人账本记 100 改 120 没有路径。INT-07 确认个人账本由本人确认更正／作废，共享账本才二审。重复凭证同理：同一交易号是强重复，拒绝且不允许写原因放行；同日同额无交易号才标疑似，由本人确认；待审核也占用交易号，作废后新建并关联原记录。

3.3.7 归档、类别、时间、非默认查询与跨月更正（REV-018；INT-07-L010—L024）

归档后只冻结账目业务写，成员退出／交接／管理员任免保留；类别停用不阻断已引用它的待审核记录，改名当前用新名、结算快照留当时名称；发生日期归账，创建时间只排序／审计，午夜补记归前一天；默认查询只返回有效记录，本人草稿／驳回／撤回、成员待审核、所有者／管理员历史版本分别按 REQ-035 查看；通知以站内可查为成功、一天内补发；跨月更正同时检查原月和新月，原账作废更正失效，提交人退出先撤回／驳回，重开后旧结算迟到不锁回旧版本。

3.3.8 审查叙述的自我校正（REV-019）

人工复核 lab1-ai-draft 原文后，REV-019 指出 REV-011 容易被读成初稿断言个人账本必须审核、REV-013 说初稿没有区分重试／凭证／同额；实际 REQ-007 原为待确认，REQ-012／014 已有保护。保留原记录，追加更准确结论：初稿把个人账本留为待确认，单人场景是组合反例排除候选；重复边界是补足判重键，而不是把已有保护说成漏洞。

### 3.4 反思、剩余风险与后续

这次最有价值的不是“让 AI 多写几条”，而是本人先用反例把含糊的规则逼成唯一结果，再让 AI 只做核对：审核与撤回谁先成功、100→120 何时切换、重试和同日同额怎么区分、结算和补记谁先。初稿把个人账本是否审核留为待确认；如果没有用单人场景去检查“必须审核＋禁止自审”的组合，候选方案会阻断个人记账——这类组合问题需要人先列出来，AI 只能核对。
