## 1 项目概况

本项目服务于需要共同记录和核对收支的多人场景，访谈以家人、情侣共享为例，同时提出个人账本。核心目标是使账本、成员、收支记录及其变更可查询、可核对，为后续设计、实现、分析和测试提供明确需求。

甲方在 INT-01-L007—L008 明确记账为核心，AI 和省钱功能为辅助。需求来源由实际访谈与课程最低项目要求共同构成；课程要求不能替代甲方对未决业务细节的回答。

| 范围 | 本版处理 |
| --- | --- |
| 核心范围 | 账本与成员、手动收支、审核和更正、组合查询、分类及成员统计、预算、结算和关键操作记录。 |
| 辅助范围待定 | 截图识别与去重的细节、AI 分析和模糊查询、通知渠道、省钱目标及进度。 |
| 尚未纳入已确认必做 | 真实资金托管、支付或转账、自动获取银行及支付平台账单。原文对可行性的判断没有经过验证，边界需补充确认。 |

### 1.1 用户角色与权限

原文具体区分账本管理员和普通成员，允许一个账本有多个管理员。课程要求至少三类不同权限角色；所有者、管理员、普通成员是工程师候选划分，REQ-004 标为待确认。

| 角色 | 已有依据与候选权限 | 未决项 |
| --- | --- | --- |
| 普通成员 | 原文提出新增记账、处理本人记录，不能删除他人记录。 | 可修改状态、本人审核、退出后历史访问。 |
| 账本管理员 | 原文提出管理所有成员记录，管理员操作也需留痕或告知。 | 审核权限、已审核和已结算记录的处理限制。 |
| 账本所有者（候选） | 建议承担管理权限交接及关键账本管理，区别于一般管理员。 | 甲方是否采用该角色与具体独有权限。 |

不同角色不能仅靠页面按钮区分。已确定的权限要在服务端对直接请求、对象标识替换等场景生效；角色矩阵尚未确定的部分不能写成已验收。

## 2 整体业务分析

### 2.1 主要业务流程

| 环节 | 主要行为 | 对应需求与边界 |
| --- | --- | --- |
| 建立账本 | 创建个人或共享账本，邀请成员加入。 | REQ-001—REQ-004；邀请接受、退出例外及角色矩阵待定。 |
| 录入账目 | 成员手动录入；截图识别是待确认的辅助入口。 | REQ-005、REQ-011—REQ-014；非法输入及重复操作须有结果。 |
| 审核变更 | 提交、通过或驳回；按允许条件修改、撤回、作废、更正。 | REQ-006—REQ-010；状态和权限细节待甲方确认。 |
| 查询统计 | 组合筛选明细，按类别、成员汇总，对照预算。 | REQ-015—REQ-018；统计有效状态与边界待定。 |
| 结算及后续 | 根据账期形成结算，再按确定策略处理历史更正。 | REQ-019—REQ-020；汇总、分摊、锁定或重开规则未定。 |
| 追溯与提醒 | 保存关键操作历史；按确定渠道通知相关成员。 | REQ-021—REQ-022；日志查询范围与通知方案未定。 |

### 2.2 主要数据之间的关系

| 对象 | 主要关系与约束 |
| --- | --- |
| 用户、账本、成员关系 | 用户与账本通过成员关系关联；同一用户与同一账本的当前成员关联不能重复。角色属于指定账本的授权，不能自动扩展至其他账本。 |
| 收支记录 | 每笔记录从属于一个账本，保留原记录人、金额、发生时间和类别等字段，使用唯一逻辑标识。退出成员的历史记录仍可追溯。 |
| 凭证及导入批次 | 截图及提取结果与入账记录关联；重复凭证和重复请求的结果需要可查，避免无提示重复入账或误合并真实消费。 |
| 审核与更正关联 | 审核人、结果、时间及更正前后内容与原账关联；采用版本修订还是其他更正方式仍需确认。 |
| 预算与结算 | 预算、明细汇总和结算必须使用明确的账本、期间及有效记录口径；结算后的变更策略见 REQ-020。 |
| 操作历史 | 关联操作者、对象、动作、时间及结果；不能随普通改删或成员退出而消失。 |

本报告不预设数据库产品或表结构实现。数据关系描述的是可验证的业务约束；对金额单位、上下限、小数位和账期边界的具体选择保留待确认。

### 2.3 业务状态和状态转换

候选核心对象为收支记录，候选有效状态为草稿、待审核、已审核、已驳回、已撤回、已作废。以下是供补充沟通的工程师模型，并非已经确认的甲方状态表。

| 候选转换 | 触发者与条件 | 待确认的关键规则 |
| --- | --- | --- |
| 草稿 → 待审核 | 创建者提交合法记录。 | 个人账本是否相同，提交后是否可编辑。 |
| 待审核 → 已审核 | 具有审核权的主体通过。 | 谁能审核，能否审核本人，旧版本如何拒绝。 |
| 待审核 → 已驳回 | 审核者驳回并保留结果。 | 理由是否必填，怎样重新提交。 |
| 待审核 → 已撤回 | 创建者在允许阶段撤回。 | 审核与撤回并发时的结果。 |
| 已驳回／已撤回 → 草稿 | 允许的主体修正内容。 | 版本与历史怎样保留。 |
| 已审核 → 已作废 | 有权主体按最终规则处理。 | 作废原因、统计调整、已结算期间是否允许。 |
| 已审核 → 更正流程 | 保留原账并建立更正关联。 | 重新审核、修订或反向更正，以及结算影响。 |

禁止绕过授权改变状态、用旧审核结果覆盖后续合法变更，或更正后无法追查原账。已审核及已结算记录不能仅凭原文“可以删除”的笼统表述实现无痕删除。完整允许和禁止转换仍需在 Q-03、Q-06 中核对。

### 2.4 异常、边界与冲突

| 场景 | 本版明确结果或待定边界 | 需求 |
| --- | --- | --- |
| 重复点击或超时重试 | 同一次提交最多一次有效记账；独立的新消费仍可区分。 | REQ-014 |
| 同一截图重复上传 | 明确判重结果，不无提示重复入账；同日同额不同消费不能仅按金额误合并。 | REQ-011—REQ-012 |
| 空值或非数字金额 | 明确提示并拒绝保存；零值、负值和小数边界待 Q-04。 | REQ-013 |
| 修改与审核同时发生 | 不得覆盖未读取的新变更；具体生效、重提及提示规则待定。 | REQ-026 |
| 退出或越权访问 | 不能误删历史关联；已确定的禁止访问必须在服务端拒绝，历史访问例外待定。 | REQ-003、REQ-027 |

| 识别或 AI 服务失败 | 不能静默写错账或改写原明细；辅助功能的具体失败策略待确认。 | REQ-011、REQ-024—REQ-025 |

### 3.3 当前结论与待完成事项

本版把访谈中的产品想法转成有来源和验收方向的完整初稿。多轮审查显示，已有条目不等于业务已经闭合：成员维度、去重边界和结算观察点仍会影响结果。AI的作用是整理、提出反例和辅助核对；它不能替甲方决定范围，也不能替学生完成尚未发生的人工确认。

尚需完成一轮真实补充沟通，并由学生逐条核对需求及 AI 辅助记录。优先明确 Q-01 角色、Q-03 记录状态、Q-06 结算，其次确定截图、通知、AI 与储钱罐边界和性能条件。即使初稿满足数量要求，核心规则待定时也不能声称最终需求已经确认。

最终应根据实际补充答复修改同一 requirements.md，保留 ID；在 chat.txt 追加真实沟通与处理理由，使报告、审查记录和实际 diff 对应。正确内容可以保留并写明核对依据，不为了制造差异诱导 AI 出错。
